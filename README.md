# rag-chatbot (Python version)

A small RAG chatbot over a fictional company handbook (Northwind Labs), built to learn AI engineering. It comes with an eval harness that scores retrieval and answer quality separately.

This branch is a straight Python port of the TypeScript version on `main`. Same data, same prompts, same behavior.

## How it works

**Once, ahead of time (`python ingest.py`)**
1. Split `data/handbook.md` into chunks, one per `## ` section.
2. Embed each chunk with Voyage AI.
3. Save text, section number and vector to `data/index.json`.

**For every question**
1. Embed the question with the same model (`input_type: "query"`).
2. Score it against every chunk with cosine similarity and keep the top 3.
3. Send the question and those chunks to the LLM (Groq, `openai/gpt-oss-120b`), with instructions to answer only from the sections and to say so when the handbook does not cover something.
4. If the question is about remaining annual leave, the model can call the `calculate_leave` tool instead of doing the math itself (see "Agent step" below).

There is no vector database. With 14 chunks, a list in memory and a loop is enough.

## Project layout

```
data/
  handbook.md      the sample handbook (14 sections)
  evals.json       test questions with reference answers
  tool-evals.json  questions with the tool arguments the model should pass
  index.json       generated by ingest.py, not committed
rag/
  chunk.py         handbook -> chunks
  embed.py         text -> vectors (Voyage), retries on 429
  retrieve.py      question -> top k chunks
  answer.py        chunks + question -> LLM (with tool loop) -> answer
  tools.py         leave calculator and its schema for the model
  judge.py         LLM-as-judge for grading answers
ingest.py          build data/index.json
ask.py             ask one question (or --retrieve-only)
run_evals.py       run all questions, print both scores
try_judge.py       check the judge on answers with known verdicts
run_tool_evals.py  check the model's tool arguments
test_tools.py      unit tests for the leave calculator, no API calls
list_models.py     list the model ids your Groq key can use
```


Keys needed:
- `VOYAGE_API_KEY` from voyageai.com (free token allowance, 3 requests per minute until a payment method is added)
- `GROQ_API_KEY` from console.groq.com (free tier, no card needed)

If Python fails with `CERTIFICATE_VERIFY_FAILED` behind a proxy or antivirus that re-signs HTTPS traffic, the `truststore` package in `requirements.txt` handles it by using your operating system's certificates. Do not disable certificate checks.

## Evals

Each entry in `data/evals.json` has a question, a reference, the section that holds the answer, and a type:

- `answerable`: the answer must match the reference in meaning
- `partial`: give what the handbook says and state what it does not cover
- `unanswerable`: say the handbook does not cover it, and invent no policy

Two numbers come out of a run:
- **Retrieval hit rate**: was the right section in the top 3? Questions with `section: null` are skipped.
- **Answer correctness**: did the LLM judge pass the answer? The judge sees the question, type, reference, the retrieved sections and the answer.

Keeping the two apart tells you what to fix. Low hit rate means chunking or embeddings. Good hit rate with bad answers means the prompt or model.

### Status

`data/evals.json` has 21 questions. Last full run on the TypeScript version (17 of these, before four older questions were restored): retrieval 14/14, answer correctness 17/17, with 2 answerable questions flagged for absence claims (both checked by hand, neither false). Seven of those 17 were written after the prompt was frozen and passed without any prompt changes, which is the evidence that the fixes are not just fitted to the original questions.

How it got there:
- The judge first failed good answers because it never saw the handbook text, and demanded facts the question did not ask for. It now gets the retrieved sections, and also the full handbook as ground truth.
- The bot kept denying the home office stipend (standing desk question) until a reminder was added right after the question in the user message. A rule plus an example in the system prompt alone did not fix it.
- That reminder also had to say what to do for partial answers, otherwise the partial questions (Q7, Q12) lost the "what is not covered" part.
- The bot volunteered false statements like "the handbook does not mention parental leave" because it only sees the top 3 sections. `run_evals.py` counts those phrases on answerable questions (about 7 before the reminder fix, 0 to 2 after).

Latest TypeScript run: 20/21. Q10 ("can I work from my sofa every day?") failed once and passed twice on re-runs. The bot gave the right rule every time but added "the handbook does not say whether working from a sofa is allowed, ask HR", which is true but puts doubt on something the rule already answers. Changes, ported here too:
- The judge now writes a check line for every "the handbook does not ..." sentence (`true: yes/no`, `matters: yes/no`), and code combines them into the verdict. Before this, the judge once wrote `matters: no` and still said CORRECT.
- Only `true: no` fails an answer. `matters` flipped between runs on the same input, so it is printed for reading but not enforced. Needless disclaimers are caught by the ABSENCE flag and a human look instead.
- The reminder in `rag/answer.py` now says a detail only counts as an uncovered part if the answer would be different depending on what the handbook said about it. Q10 no longer sends the employee to HR about the sofa, and the partial questions Q17 and Q19 still say what is missing.
- `run_evals.py` takes ids (`python run_evals.py 10 17`) and `try_judge.py` takes case names (`python try_judge.py F B`, which also prints the full reason), to save tokens. Groq's free tier has a 200,000 tokens per day cap, and a full run uses about 100,000.

Next full TypeScript run: 19/21. Q2 and Q7 failed, and reading them showed the bot dropped important details. Changes, ported here too:
- Q2 said "approved overtime" but not that approval must come before the overtime is worked. Its reference now says the advance approval is required, and a system prompt rule tells the bot to state conditions (approvals, deadlines, documents, eligibility) exactly, including when they must happen. Q2 then passed 3/3. Case H in `try_judge.py` checks that the old answer now fails.
- Q7 said "there is no separate maternal leave", treating the gap as a naming issue. The real gap is that parental leave starts at the birth, so leave during pregnancy is not covered. Its reference now requires saying so, and a system prompt rule tells the bot to compare the employee's situation with what the policy covers (who, when it starts and ends), not words with words. By hand: no rule 0/3, rule in the system prompt 3/6, rule also in the reminder 0/3 (reverted).
- Side-effect checks: Q5 and Q21 kept their conditions without padding, Q17 and Q19 kept their real gaps, Q10 was clean in two runs.
- The judge sometimes returned empty text, because `gpt-oss` spends `max_tokens` on thinking first. It now has `max_tokens: 3000` and raises an error on an empty reply instead of counting it as a FAIL.

Latest full TypeScript run: 20/21 with 0 absence claims. Q7 failed (it passes about half the time), and Q2, Q8 and Q10 gave their best answers so far.

## Agent step: the leave calculator

"I joined on 2020-03-01 and used 8 days, how many are left?" needs today's date and arithmetic. The model has no clock, and it guesses the date from its training data, so the date math and subtraction live in code (`rag/tools.py`):

- **Split of work:** the model reads the employee's numbers from the question and the rule numbers (20, 25, 5 years, max 5 carried over, expiry 03-31) from the retrieved handbook section, and passes them in. The code applies the rules. Keeping the rule numbers as inputs means the handbook stays the single source of truth.
- **Input checks:** a bad date, a date that does not exist (2020-02-30), a future join date or negative days return an error message to the model instead of raising, so the model can ask the employee for what is missing. A missing or wrongly typed argument is also returned to the model as an error.
- **Results the model can explain:** the tool returns the intermediate facts (days claimed, allowed after the maximum, counted after expiry), not only `remaining`. Without them the model sometimes said "you carried over 7, so none count", which is not the rule.
- **The loop** (`rag/answer.py`): call the model with the tool, run any tool calls, add the results to the conversation, repeat. `MAX_STEPS = 3` stops a model that keeps calling the tool, since every step resends the whole conversation and uses tokens.

Testing it, in two parts:
- `python test_tools.py`: unit tests for the calculator with a fixed "today", so results never change with the calendar. They include boundaries (the day before and on the 5th anniversary, 31 March and 1 April) and a 29 February join date (anniversary on 1 March in other years, the same as the TypeScript version).
- `python run_tool_evals.py` (`data/tool-evals.json`): checks the model's tool arguments exactly, and that it does not call the tool when it should not (a sick leave question, a vague join date). No judge. The final number depends on today's date, the arguments do not.

What the tool evals caught on the TypeScript version:
- The model asked the employee for "the current year" instead of calling the tool. Fixed by saying in the tool description that it knows today's date.
- For "I carried over 7 days" (over the 5-day maximum) the model skipped the tool 3 of 3 times and did the math itself. It got the right number by assuming the year is 2026, which would be wrong next March. A check of the final answer alone would have passed it. Fixed by saying in the `carriedOver` description to pass exactly what the employee said and that the tool applies the maximum (then 5 of 6 runs called the tool).

Open: first-year proration ("an employee who joins mid-year receives a prorated amount") is not handled, and "leave accrues monthly" is ambiguous, so it needs an answer from HR first.

Known weak spots:
- Q7 (pregnancy) passes about half the time. A likely fix is to have the bot write the employee's situation and what the policy covers before answering, as the judge does with its check lines, and hide those notes from the employee.
- The judge catches blatant mistakes (`try_judge.py` cases A to D) but can pass a softer one, such as stretching the lost/stolen rule to cover damage (case E), or a true but needless disclaimer (case F).
- Both the bot and the judge vary between runs even at temperature 0. On borderline questions, compare totals over several runs and read the answers.
- Seven held-out questions is a small sample.

This Python port has not been run against the live APIs. It was checked offline: every file compiles, and chunking, cosine similarity, retrieval ranking, request shapes, the retry on 429, judge verdict parsing and the absence-claim pattern were tested with fake data. The tool loop was tested with a fake Groq: a tool call goes to the calculator and its result back to the model, and the step cap stops after 3 calls.
